## ADR-0015 — Exception Ownership and Translation Rules

**Status:** Accepted

### Context & Rationale

The module interacts with external and technical concerns such as:

- network access
- SDKs and platform APIs
- persistence layers
- rate limiting and execution constraints

These interactions naturally fail in technical ways that must be:

- isolated from the Domain
- translated at clear architectural boundaries
- exposed to the Application in a controlled, semantic manner

Without clear ownership rules, exceptions risk leaking across layers, causing:

- domain pollution
- infra-driven application logic
- inconsistent error handling

This ADR defines **where exceptions live**, **who may throw them**, and **where translation occurs**.

---

### Decision

Exceptions follow the **same inward flow as dependencies**.

> **Exceptions are translated as they move inward.**  
> **No exception crosses more than one architectural boundary unmodified.**

Each layer owns its own failure vocabulary, and translation happens at the **first inward boundary**.

---

## Exception Categories and Ownership

### 1. Domain Failures

**Owned by:** Domain  
**Canonical location:** `lib/src/core/domain/failures/`

Failures are the module’s **semantic error vocabulary**.

- Expressed in the module’s ubiquitous language
- Stable across UI/SDK/storage replacements

Rules:

- A `Failure` represents a **business or repository outcome**
- Failures are thrown by repositories to signal domain-aligned failure conditions.
- Technical exceptions MUST be translated into Failures at repository or use-case boundaries

Produced by:

- domain entities/value objects/domain services (business invariants)
- data repositories (translation result)

> Note: Repositories returning Failures instead of throwing them was considered, but it would require all repositories to return `Either<Failure, T>`, including those that uses `TransactionRunner` (Application Port defined in ADR-0017), requiring that Infra Adapters also handle the Failure explicitly - which would leak domain semantics into Infra and create a lot of boilerplate.

Example:

- `AnnualRevenueGoalRepFailure`

---

### 2. Use Case Failures (Application - Feature-specific)

**Owned by:** Application (Feature)  
**Canonical location:**  
`lib/src/features/<feature>/application/use_cases/<use_case>/failures/`

Use-case failures represent **user-story-level error semantics**.

- Translate domain failures and port exceptions
- Are what the Presentation layer branches on

Rules:

- Use cases MUST NOT throw technical exceptions
- Use cases MUST return `Either<Failure, T>`
- Use cases MUST NOT expose Data or Infra exception types

Example:

- `CreateAnnualRevenueGoalFailure`

---

### 3. Data Technical Exceptions

**Owned by:** Data  
**Canonical location:** `lib/src/core/data/exceptions/`

Data exceptions represent technical failures limited to persistence or IO boundaries.

- Purely technical
- No business meaning
- Never exposed to Application or Presentation

Thrown by:

- Infra data source implementations (after translating SDK/platform errors)

Caught and translated by:

- Data repository implementations

Examples:

- `ServerException`
- `RateLimitExceededException`

---

### 4. Port Error Signaling

Ports do not own a failure or exception vocabulary.

- Ports define **capabilities only**, not error semantics
- There is **no dedicated location** for port failures or exceptions
- Ports do not expose typed error contracts

---

Rules:

- Application MUST NOT depend on Infra exception types thrown by ports
- Data Sources MUST translate SDK/driver exceptions from Infra into Data Exceptions
- Use Cases are responsible for translating exceptions thrown by ports into `Failure`

> Note: Generic exceptions captured by Application are treated as opaque failure signals, not as sources of information.

Guiding principle:

> Ports define *what the application needs*, not *how or why it fails*.

---

## Translation Boundaries

### Infra → Data

- Infra data sources translate SDK/driver errors into Data exceptions
- Data repositories translate Data exceptions into Domain Failures

---

### Infra → Application

- Infra adapters implement Application Ports
- Infra adapters translate SDK errors internally and throw generic exceptions to signal failure
- Use cases translate port errors into use-case failures

---

## Hard Rules

- Domain MUST NOT know about exceptions from any other layer
- Infra adapters MAY throw generic `Exception` to signal failure
- Application MAY catch generic `Exception` but MUST NOT reference
  Infra- or Data-owned exception types, neither use them for control flow/conditional branching
- Exceptions MUST be translated at the first inward boundary
- Presentation MUST NOT branch on technical exceptions

---

## Consequences

- Error handling is predictable and consistent

This enables clean evolution:

- swapping SDKs or persistence affects only Infra/Data
- repository failure translation remains stable
- Presentation remains stable by depending only on use-case failures
