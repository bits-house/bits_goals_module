## ADR-0018 — Transaction-Aware Data Repositories implementations

**Status:** Accepted

---

### Context & Rationale

In use cases that require cross-module/app orchestration (ADR-0017), multiple data repositories must operate within the same atomic boundary.

- Transaction orchestration is owned by the **Application layer** via `TransactionRunner`.
- `AppTransaction` is not an infrastructure implementation detail.
- It represents an **Application-level consistency boundary**.

Therefore:

Accepting an `AppTransaction` does **not** automatically make an interface technical.

---

### Decision

#### A) Data Repositories implementations MAY be Transaction-Aware

A repository defined in Data:

- MAY accept `AppTransaction`
- WITHOUT becoming an Infra adapter or technical service

When:

- It does not depend on any technical/environmental service (e.g., SDK, network, device)

In this case:

`AppTransaction` is treated as an **Application Port/Contract**, not an infrastructure concern.

### Consequences
- Repositories can be transaction-aware without breaking architectural boundaries.
- The Application layer can orchestrate transactions across multiple repositories, even if they are implemented in Data, without forcing those repositories to depend on Infra or become technical.
- Data repositories remain pure and free of technical concerns, while still supporting transaction orchestration when needed.
