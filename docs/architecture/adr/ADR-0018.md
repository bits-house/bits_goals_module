## ADR-0018 — Domain Repositories vs Application Ports that look like Repositories

**Status:** Accepted

### Context & Rationale

In use cases that require cross-module/app orchestration (ADR-0017), we often need to define interfaces that:
- are used to persist domain entities and other related data.
- accept an `AppTransaction` to ensure all operations share the same transaction boundary.

These interfaces are technically “repositories” in the sense that they abstract data operations, but they are not **Domain Repositories** because:
- They are **transaction-aware** (accept `AppTransaction`), which is a technical concern, not a domain concept.
- They are primarily **integration adapters** for cross-module/app workflows, not pure domain persistence contracts.

This ADR clarifies when each type (Domain Repository vs Application Port) should exist and where it belongs, for cross-module/app orchestration.

### Decision

#### A) When to define a Repository in Domain

Define a **Domain Repository contract** in Domain when:

- It expresses a **domain persistence need** (aggregates, entities, domain queries) in domain language.
- The interface can remain **pure**:
  - MUST NOT depend on `AppTransaction` or any Application/Infrastructure concerns.
- It represents a capability that should remain stable even if storage technology changes.

#### B) When to define an Application Port that “looks like a repository”

Define an **Application Port** (even if it resembles a repository) in Application when:

- The interface is **transaction-aware** (accepts `AppTransaction`).
- The interface represents a **technical integration concern**.

Important rule:

- Any interface that requires `AppTransaction` MUST NOT live in Domain (ADR-0014). It MUST be modeled as an Application Port.

Naming guidance (to avoid confusion with Domain repositories):

- Do not name it `...Repository`.
- Instead, name it as an integration port/adapter that reflects its intent (e.g., `OrdersWriter`, `GoalsProgressUpdater`).

Canonical location:

- `lib/src/core/application/ports/integration/...` or `lib/src/features/<feature>/application/ports/integration/...`

#### C) Where implementations live

- **Domain repository implementations** live in Data (ADR-0014).
- **Application port implementations** live in Infra as adapters (ADR-0011, ADR-0014).

#### D) Who defines the transaction boundary

- Only **Use Cases** define the transaction boundary (begin/commit/rollback) (ADR-0017).
- Infra may accept/use `AppTransaction` but MUST NOT create/own the boundary.

### Consequences

- Domain stays free of technical transaction concepts (`AppTransaction`).
- “Repository” regains a single meaning: a domain persistence contract.
- Integration-heavy, transaction-aware interfaces are correctly modeled as Application Ports.
- Use Cases remain the single entry point and orchestrator of cross-step atomicity.
