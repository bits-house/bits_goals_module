## ADR-0011 — Technical services are modeled as Application Ports (not Domain Services)

**Status:** Accepted

### Context & Rationale

The module needs to interact with technical/environment concerns such as:

* permissions / access control
* request/execution metadata (app version, device info, ip address)
* rate limiting
* network/device/app info

These concerns are **not** domain services. Even as interfaces, naming and placement inside `domain/` causes the domain to “know” about technical concepts and invites dependency drift.

Instead, use: **ports** (interfaces owned by the application) with **implementations in infra**.

### Decision

All technical/service interfaces that represent **how the application talks to the outside world** MUST be defined as **Application Ports** and implemented in **Infra** as services (adapters).

Canonical locations:

* `lib/src/core/application/ports/...` for shared ports
* `lib/src/features/<feature>/application/ports/...` for feature-specific ports (if needed)

Domain services are reserved only for business rules that:

* do not fit inside an entity/value object
* express domain language
* orchestrate business concepts (e.g., splitting an annual goal)

### Consequences

* Domain stops “speaking” technical language.
* Port ownership is clear: the application defines what it needs.
* Infra can evolve without leaking platform/app concepts into domain.
