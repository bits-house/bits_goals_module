## ADR-0014 — Dependency Flow and Layer Import Rules

**Status:** Accepted

### Context & Rationale

The project follows Clean Architecture (ADR-0002) and is organized into Core, Features, Infra, and Presentation layers.

Within `lib/src`, the codebase is structured into **five architectural layers**, each with a clear responsibility and dependency direction:

- **Domain** — business language and rules
- **Application** — orchestration and system intent
- **Data** — persistence-facing implementations and IO translation
- **Infra** — external integrations, SDKs, and platform details
- **Presentation** — UI, controllers, and delivery mechanisms

Without explicit rules, ambiguity arises around:

- UI logic leaking into use cases
- presentation depending directly on infra or data
- unclear error propagation across layers
- DTOs and models being shared incorrectly

This ADR formalizes **dependency flow and import rules** to prevent architectural drift.

---

### Decision

The module follows a **strict inward dependency rule**:

```text
Presentation → Application → Domain
Infra → Data → Application → Domain
```

Notes: 

> The Data layer depends on both Application (contracts only) and Domain.

> Although depicted as 2 flows, this does not represent two pipelines.

> All dependencies still point inward. Data and Infra are both outer layers from the perspective of Application and Domain.

Which means:

- Presentation depends only on Application (and Domain types as read-only data)
- Application depends only on Domain
- Data depends on Application contracts
- Data depends on Domain (entities, failures, repository contracts, etc.)
- Infra depends on Application and Data contracts

Inner layers MUST NEVER import outer layers.

There is **no direct dependency** from Presentation to Infra or Data.

---

## 1. Domain Layer

The Domain layer:

- MUST NOT depend on any other layer
- MUST NOT import anything from:
  - Application
  - Data
  - Infra
  - Presentation

The Domain contains only **business concepts and rules**, expressed in ubiquitous language:

- entities
- value objects
- domain services
- policies
- failures
- repository contracts

The Domain never references UI, frameworks, SDKs, persistence, or application flow.

Canonical locations:

- `lib/src/core/domain/entities/...`
- `lib/src/core/domain/value_objects/...`
- `lib/src/core/domain/services/...`
- `lib/src/core/domain/policies/...`
- `lib/src/core/domain/failures/...`
- `lib/src/core/domain/repositories/...`
- `lib/src/core/domain/utils/...`

---

## 2. Application Layer

The Application layer:

- MAY depend on Domain
- MUST NOT depend on Data, Infra, or Presentation

The Application layer OWNS:

- use cases (application orchestration)
- ports (interfaces for technical/environment services)
- DTOs required by use cases or ports

Notes:

> Application DTOs are objects only consumed by use cases, not API, database, or UI models.

> Repository contracts belong to the Domain because persistence is a business concern, while technical services (network, device, rate limiting) are application concerns, that's why ports live in Application.

The Application defines **what the system does**, not **how it is delivered or implemented**.

Clarifications:

- Repository contracts live in **Domain**.
- Technical services (network, device, metadata, rate limiting, etc.) are modeled as **Application Ports** (ADR-0011).

Canonical locations:

- Use cases (shared): `lib/src/core/application/use_cases/...`
- Use cases (feature): `lib/src/features/<feature>/application/use_cases/...`
- Ports: `lib/src/core/application/ports/...`
- Port DTOs: `lib/src/core/application/dtos/...`

---

## 3. Data Layer

The Data layer acts as a boundary adapter layer, isolating persistence concerns and translating them into domain concepts.

The Data layer:

- MAY depend on:
  - Domain (entities, value objects, failures, repository contracts)
  - Application contracts ONLY
- MUST NOT depend on:
  - Application use cases
  - Presentation
  - Infra implementations

Responsibilities:

- implement Domain repository contracts
- translate technical/IO exceptions into Domain failures
- map data models ↔ domain entities
- isolate persistence concerns from application flow

Rule:

> **Data may import Application contracts, but never Application behavior.**

Canonical locations:

- Data source contracts: `lib/src/core/data/data_sources/...`
- Repository implementations: `lib/src/core/data/repositories/...`
- Data exceptions: `lib/src/core/data/exceptions/...`
- Models: `lib/src/core/data/models/...`
- Mappers: `lib/src/core/data/mappers/...`
- Extensions: `lib/src/core/data/extensions/...`

---

## 4. Infra Layer

The Infra layer contains **technology- and platform-dependent code**.

The Infra layer:

- MAY depend on:
  - Application contracts (ports, DTOs)
  - Data contracts and Data exceptions
  - Domain types only when required by an interface
- MUST NOT depend on:
  - Application use cases
  - Presentation
  - Create or decide Domain failures

Responsibilities:

- implement Application Ports (adapters)
- implement Data Source contracts using SDKs, APIs, OS features
- deal with IO, platform, and third-party integrations

Infra MUST NOT:

- implement business rules
- orchestrate application flows
- translate errors into domain failures

Canonical locations:

- Port adapters: `lib/src/infra/adapters/...`
- SDK-backed data sources: `lib/src/infra/data_sources/...`

---

## 5. Presentation Layer

The Presentation layer is the **outermost layer** and the system’s entry point.

The Presentation layer:

- MAY depend on:
  - Application (use cases)
  - Domain (read-only data types only)
- MUST NOT depend on:
  - Data
  - Infra implementations
  - Technical exceptions

Responsibilities:

- UI rendering (widgets, views, screens)
- user input handling
- state management
- mapping user actions → use case execution
- mapping use case results → UI state

Rules:

- Presentation MUST call **Application use cases only**
- Presentation MUST NOT contain business rules
- Presentation MUST NOT access repositories, data sources, or infra services directly

Canonical locations:

- `lib/src/features/<feature>/presentation/...`
- `lib/src/core/presentation/...`

---

## Consequences

- Dependency flow is explicit and enforceable.
- Application controls orchestration and system behavior.
- Domain remains pure and stable.
- Data and Infra remain implementation details.
- UI changes never force changes inward.
