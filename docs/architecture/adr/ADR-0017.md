## ADR-0017 — TransactionRunner for cross-module/app transactional orchestration (integration use cases)

**Status:** Accepted

### Context & Rationale

This module follows Clean Architecture (ADR-0002) with strict inward dependencies (ADR-0014) and explicit failure/error rules (ADR-0015).

Most operations that need atomicity are naturally bounded to a **single repository** (e.g., persisting an aggregate + its logs). In those cases, the repository implementation can guarantee atomicity internally.

However, the plugin is designed to be reused across applications (ADR-0001) and may need to participate in **cross-module/app workflows** (ADR-0016), where a host application (or another module) must update:

- its own state (e.g., an Order)
- and this module’s state (e.g., goals progress)

…as a single atomic unit.

To support that without creating forbidden dependencies (e.g., Goals depending on Orders) or depending on third party event-driven mechanisms, this module provides a storage-agnostic transaction boundary:

- `TransactionRunner` (Application Port)
- `AppTransaction` (transaction context)

with concrete implementations living in Infra and configured/orchestrated by the host app.

### Decision

**Use Cases are the only entry point for TransactionRunner.**

Per ADR-0014, the **only** valid entry point into the system behavior is the **Application layer** via **Use Cases**.

Therefore:

- `TransactionRunner` is an **Application Port**.
- `TransactionRunner` MAY be used **only by Application Use Cases** to start and orchestrate a transaction.
- `TransactionRunner` MUST NOT be used directly by Presentation, Data, or Infra.

`TransactionRunner` MAY be used **only** when one of the following is true:

1. **Cross-module/app integration** is required (e.g., host app updates its own data and also updates goals progress in this plugin), or
2. There is a need to **reuse a transaction boundary** across multiple writes in a way that cannot be reasonably encapsulated inside a single repository operation.

#### Why the transaction boundary is application responsibility

Defining a transaction boundary (begin/commit/rollback) is an **orchestration decision**: it answers *which operations must be atomic together* and *in what order*.
That decision belongs to the **Application layer**, because, when it comes to **integration**, it is part of the use case intent between modules, not just a persistence implementation detail.

It cannot live in Domain because Domain must be pure and must not orchestrate application flows (ADR-0014).

It should not live in Data because Data does not have the full use-case workflow context.

It cannot live in Presentation because Presentation must not access repositories (ADR-0014) and should not be responsible for application flows or integration concerns.

And it should not live in Infra either: Infra is responsible for the *mechanics* of integration (SDK calls, drivers, IO) and is explicitly not responsible for orchestrating application flows (ADR-0014).

If Infra owned the boundary, it would need to know which application steps must be atomic together (a use-case concern), and it would become coupled to specific use cases / workflows (inverting the intended dependency direction).

Since the atomic block semantics are driven by the use-case intent, the only stable and correct place to declare the atomic block is the Application layer, specifically the Use Case.

#### Placement & dependency rules

- `TransactionRunner` and `AppTransaction` contracts live in `lib/src/core/application/ports/transaction/`.
- Concrete implementations live in **Infra**.
- **Use Cases** are the transaction entry point: they may depend on `TransactionRunner`, call `run(...)`, and pass the `AppTransaction` down.
- **Data** layer may accept/use `AppTransaction` only via **Application contracts** (ADR-0014) and MUST NOT create/own transaction boundaries.
- **Domain** MUST NOT import `AppTransaction` or `TransactionRunner` (ADR-0014). Any interface that requires `AppTransaction` is, by definition, a technical integration concern and therefore must be modeled as an **Application Port**, not a Domain repository.

Hard rule:

- Only Use Cases may decide the transaction boundary (begin/commit/rollback).

#### Failure/commit semantics

To align with ADR-0015 (ports do not expose typed error contracts; Infra adapters may throw generic `Exception`):

- The `TransactionRunner.run` action MUST signal failure by throwing a generic `Exception`.
- When the action completes successfully, the transaction MUST commit.
- If the action throws, the transaction MUST roll back and rethrow a generic `Exception`.

Use cases catch this generic exception and translate it into their own `Failure` (ADR-0015).

### Consequences

- Cross-module/app workflows can be atomic without introducing forbidden dependencies or relying on third-party event-driven mechanisms.
- Domain remains pure and independent of transactional/infra concepts.
- Transaction boundaries remain explicit at the **use-case orchestration** level.
- Internal operations should still prefer repository-level atomicity; `TransactionRunner` is a tool for integration and coordination, not a default for every use case.
