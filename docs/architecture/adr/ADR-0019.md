## ADR-0019 — Store-driven Presentation Architecture (non-MVVM)

**Status:** Accepted

### Context & Rationale

This module follows Clean Architecture (ADR-0002). This ADR defines how the Presentation layer is structured within that overall architecture.

Flutter projects commonly formalize the Presentation layer around one of the following approaches:

- MVVM with reactive viewModels (often MobX-based)
- BLoC / Cubit
- Provider-based reactive viewModels

This module initially used an MVVM-like structure, but the needs of the system evolved toward a model where:

- UI behavior is easier to reason about with **explicit unidirectional flow**.
- **Persistent UI state** must be clearly separated from **ephemeral events** (e.g., navigation, snackbars).
- Rebuild triggers must be predictable and test-friendly.
- The Presentation layer must remain **decoupled from any specific reactivity framework**.

In traditional MVVM (as commonly applied in Flutter with MobX), it is common to:

- Mix persistent state and one-off events in the same reactive graph.
- Represent “do something once” actions as state, which can be re-observed and re-triggered.
- Depend on code generation and implicit reactivity rules.
- Use fine-grained observables that can lead to invalid states.

Observed failure modes for this style include:

- Snackbars/dialogs triggered multiple times after rebuilds/hot reloads.
- Flutter context-related issues when effects are triggered outside of the widget lifecycle.
- Difficulty defining ownership and lifecycle of resources like streams, controllers, and subscriptions.
- Higher risk of invalid transitional states when state is not modeled as a closed set.

At the same time, adopting BLoC as the official architecture was not aligned with the desired ergonomics:

- It enforces an explicit Events layer and reducer-like structure, increasing boilerplate.
- It imposes a relatively rigid shape for all screens, even when not needed.
- It does not naturally model “implicit UI intents” (e.g., scroll proximity triggering pagination) without additional glue.

The chosen direction is pragmatic and MVI-inspired.

### Decision

Define the Presentation layer as a **Store-driven architecture** with explicit unidirectional flow.

#### A) Store as the single authority

Each screen (or cohesive UI scope) is driven by a `Store<S, E>` responsible for:

- Holding the persistent screen state `S`.
- Emitting ephemeral effects `E`.
- Coordinating state transitions through methods.
- Owning and disposing any resources it creates.

Hard rules:

- UI MUST NOT mutate state directly.
- All state transitions MUST occur through Store methods representing user intents.
- `S` MUST represent the whole UI state as a sealed state machine (closed set of valid states).
- `E` MUST represent one-off effects (navigation, snackbars, dialogs, etc.) and MUST NOT be modeled as persistent state.

#### B) Observers project Store output into UI

UI widgets connect to Stores via observer widgets.

- `AppObserver<ST, S, E>`:
	- rebuilds only when `S` changes
	- listens to `effects` without rebuilding
	- manages Store lifecycle (including disposal)
	- provides the Store to the subtree via `AppProvider`

This makes the widget tree a projection of `S` and prevents effects from being accidentally re-fired as a consequence of rebuilds.

#### C) Specialized observers for specialized UI problems

When a problem requires more than “rebuild on state change”, introduce a specialized Store/Observer pair that still follows the same core rules.

Example: `AppStreamedListStore` + `AppStreamedListObserver` for limit-based infinite scrolling.

Responsibilities handled by the specialized observer include:

- Pagination footer rendering based on a separate `PaginationState`.
- Animated insertions via `SliverAnimatedList` diffing.
- Translating implicit UI intent (scroll proximity) into Store method calls (`loadMore`) without leaking pagination rules into UI or feature-specific Stores.

#### D) Reactivity is an implementation detail, not an architectural pillar

The architecture defines reactive contracts but does not mandate a specific engine.

Signals-style approaches were considered but not adopted due to current ecosystem maturity and long-term maintenance risk.

ChangeNotifier was also evaluated as a potential reactive engine. However, as state complexity grows — particularly with the introduction of derived (computed) values — dependency management would become significantly more complex and error-prone. Unlike systems with automatic dependency tracking such as MobX, using ChangeNotifier would require manual orchestration of notifications across multiple state sources, increasing coupling and cognitive maintenance cost. While viable for simpler scenarios, it was ultimately not adopted because it introduces structural complexity precisely where declarative reactivity provides the most value.

- `AppReactivity<T>` defines framework-agnostic reactive read + listener semantics.
- `AppObservableReactivity<T>` defines a mutable reactive primitive.

Current implementation:

- `AppObservable<T>` wraps MobX `Observable<T>`.
- It uses `reaction` internally to notify listeners.
- It does not require code generation.

MobX is therefore used as an internal mechanism, not as an exposed architectural dependency. A different engine (signals, streams, `ValueNotifier`, etc.) can replace `AppObservable` without changing Store/UI contracts.

### Consequences

Positive:

- Unidirectional flow is explicit: UI reads state and calls Store methods.
- Effects are not re-triggered by rebuilds/hot reloads, because they are separate from state.
- Stores are testable as pure state machines with explicit transitions and effect emissions.
- The Presentation layer is not coupled to MobX, code generation or any specific reactive framework.
- Specialized observers can exist without breaking the core model.

Trade-offs / constraints:

- `S` requires disciplined modeling and equality semantics; incorrect equality (e.g., in observer widgets) can lead to missed rebuilds or extra rebuilds.
- Store lifecycle ownership must be explicit (observers may dispose Stores; sharing requires clear ownership).

### Alternatives Considered (not for the engine but for the overall presentation architecture)

#### A) MVVM with MobX

Pros:

- Familiar in the Flutter ecosystem.
- Good ergonomics for reactive UI.
- Fine-grained observables can be efficient.

Reasons not adopted as the official architecture:

- Common MVVM usage mixes persistent state and ephemeral events.
- Typically leans on code generation and MobX concepts being part of the public architecture.
- Encourages fine-grained observables that can make screen-level reasoning harder when not bounded by a sealed state machine.
- In the adopted architecture, fine-grained observables can still exist as an implementation of a custom Store Template for specific cases if needed.

#### B) BLoC / Cubit

Pros:

- Strong unidirectional model.
- Clear separation of intent and state.
- Well-known patterns and libraries in the Flutter ecosystem.
- Highly testable with explicit events and states.

Reasons not adopted:

- Boilerplate overhead (events, reducers/handlers) for many screens.
- Does not naturally model the separation of persistent state and one-off effects without additional patterns.
- Constrains the architecture to a specific pattern that may not fit all screen needs (e.g., complex screens with multiple state sources that require fine-grained control due to performance considerations), whereas the chosen Store-driven approach allows for more flexibility while still enforcing core principles.

#### C) Provider-based reactive ViewModels / ChangeNotifier-style patterns

Pros:

- Simple to wire in Flutter.
- Low barrier to entry.

Reasons not adopted:

- Effects commonly leak into state and can be re-fired.
- Does not enforce sealed-state modeling or explicit unidirectional flow.
- As state complexity grows, manual dependency management becomes error-prone.
