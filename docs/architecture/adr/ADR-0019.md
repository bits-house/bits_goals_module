## ADR-0019 — Store-driven Presentation Architecture (non-MVVM)

**Status:** Accepted

### Context & Rationale

This module follows Clean Architecture (ADR-0002). This ADR defines how the Presentation layer is structured.

Flutter projects commonly formalize the Presentation layer around one of the following approaches:

- MVVM with reactive ViewModels (e.g., MobX, Provider + ChangeNotifier)
- BLoC / Cubit

This module was initially planned to use an MVVM structure, but the needs of the system evolved toward a model where:

- **UI state** must be clearly separated from **ephemeral events** (e.g., show snackbars for success/failure).
- **UI state** must be predictable and test-friendly.
- The Presentation layer must remain **decoupled from any specific reactivity framework**.
- **UI behavior** is easier to reason about with **explicit unidirectional flow**.

In traditional MVVM (as commonly applied in Flutter with MobX), it is common to:

- Mix persistent state and one-off events in the same reactive graph.
- Represent “do something once” actions as state, which can be re-observed and re-triggered.
- Depend on code generation and implicit reactivity rules.
- Use fine-grained observables that can lead to invalid states.

Observed failure modes for this style include:

- Snackbars/dialogs triggered multiple times after rebuilds/hot reloads.
- Flutter context-related issues when effects are triggered outside of the widget lifecycle.
- Difficulty defining ownership and lifecycle of resources like streams, controllers, and subscriptions.
- Higher risk of invalid transitional states when state is not modeled as a closed set.

At the same time, adopting BLoC as the official architecture was not aligned with the desired ergonomics:

- It enforces an explicit Events layer and reducer-like structure, increasing boilerplate.
- It imposes a relatively rigid shape for all screens, even when not needed.
- It does not naturally model the separation of persistent state and one-off effects without additional patterns.

The chosen direction is pragmatic and MVI-inspired.

### Decision

Define the Presentation layer as a **Store-driven architecture** with explicit unidirectional flow.

#### A) Store as the single authority

Each screen (or cohesive UI scope) is driven by a `Store<S, E>` responsible for:

- Holding the persistent screen state `S`.
- Emitting ephemeral effects `E`.
- Coordinating state transitions through methods.
- Owning and disposing any resources it creates.

Hard rules:

- UI MUST NOT mutate state directly.
- All state transitions MUST occur through Store methods representing user intents.
- `S` MUST represent the whole UI state as a sealed state machine (closed set of valid states).
- `E` MUST represent one-off effects (navigation, snackbars, dialogs, etc.) and MUST NOT be modeled as persistent state.

#### B) Observers project Store output into UI

UI widgets connect to Stores via observer widgets.

- `AppObserver<ST, S, E>`:
	- rebuilds only when `S` changes
	- listens to `effects` without rebuilding
	- manages Store lifecycle (including disposal)
	- provides the Store to the subtree via `AppProvider`

This makes the widget tree a projection of `S` and prevents effects from being accidentally re-fired as a consequence of rebuilds.

#### C) Specialized observers for specialized UI problems

When a problem requires more than “rebuild on state change”, introduce a specialized Store/Observer pair that still follows the same core rules.

Example: `AppStreamedListStore` + `AppStreamedListObserver` for limit-based infinite scrolling.

Responsibilities handled by the specialized observer include:

- Pagination footer rendering based on a separate `PaginationState`.
- Animated insertions via `SliverAnimatedList` diffing.
- Translating implicit user intent (load more data), by scroll proximity, into Store method calls (`loadMore`) without leaking pagination rules into UI or feature-specific Stores.

That way, every Store created extending `AppStreamedListStore` can get this behavior for free without needing to re-implement it. That ensures no boilerplate and no duplication of complex UI logic across feature-specific Stores, that can have only feature-specific state. All that, while deals with the list internal state in a performative and fine-grained way, updating the UI in real-time, based on both user interaction and data source changes.

#### D) Reactivity is an implementation detail, not an architectural pillar

The architecture defines reactive contracts but does not mandate a specific engine.

- `AppReactivity<T>` defines framework-agnostic reactive read + listener semantics.
- `AppObservableReactivity<T>` defines a mutable reactive primitive.

Current implementation:

- `AppObservable<T>` wraps MobX `Observable<T>`.
- It uses `reaction` internally to notify listeners.
- It does not require code generation: Extending `AppStore` in a feature-specific store is sufficient to implement reactive state management without boilerplate and code generation, where `setState` (store method) can be used to update state and trigger `AppObserver` rebuilds, and `emitEffect` can be used to trigger one-off effects.

MobX is therefore used as an internal mechanism, not as an exposed architectural dependency. A different engine (like signals) can replace `AppObservable` implementation without changing Store/UI contracts.

Signals-style approaches were considered but not adopted due to current ecosystem maturity and long-term maintenance risk.

ChangeNotifier was also evaluated as a potential reactive engine. However, as state complexity grows — particularly with the introduction of derived (computed) values — dependency management would become significantly more complex and error-prone. Unlike systems with automatic dependency tracking such as MobX, using ChangeNotifier would require manual orchestration of notifications across multiple state sources, increasing coupling and cognitive maintenance cost. While viable for simpler scenarios, it was ultimately not adopted because it introduces structural complexity precisely where declarative reactivity provides the most value.

### Consequences

Positive:

- Unidirectional flow is explicit: Store updates state -> UI reads the state (and sets intent, but does not directly modify state).
- Effects are not re-triggered by rebuilds/hot reloads, because they are separate from state.
- Stores are testable as pure state machines with explicit transitions and effect emissions.
- The Presentation layer is not coupled to MobX, code generation or any other specific reactive framework.
- Specialized observers can exist without breaking the core model.

Trade-offs / constraints:

- Creating specialized observers and store "templates" can be a trade-off: more work upfront, but it pays off in the long run by centralizing complex UI logic and providing a clear contract for screens with no boilerplate.
- This approach is not maintained by a community or a company, so it requires internal ownership and maintenance that would not be a concern using a well-supported framework. However, it is relatively simple and framework-agnostic, which should mitigate long-term risks.
- If state is not explicitly passed to the child widget via constructor, Flutter may reuse the existing widget and skip its rebuild — even when the Store state changes and the Observer rebuilds. This happens when the child widget stays in the tree (is not disposed) while the state it should reflect has changed. In this scenario, Flutter keeps the existing widget instance with its previous configuration instead of rebuilding it. This is not an AppObserver failure nor a Store issue — it is Flutter’s normal reconciliation behavior when deciding whether a widget needs rebuilding. For this reason, state must be explicitly passed via constructor (or locally observed) in widgets that are expected to update without being disposed (expected to have consecutive rebuilds), otherwise UI updates may be missed. This is a general Flutter consideration, not specific to this architecture, but it is an important pitfall when using a Store-driven approach. When applied correctly, this behavior is beneficial for performance, as it avoids unnecessary rebuilds of child widgets that do not depend on consecutive changing state — and passing state via constructor removes the need for those widgets to have their own observers or being stateful widgets. The only point that needs attention is that the state should not be passed way too deep in the tree, otherwise it can lead to boilerplate and coupling between the Store and deeply nested widgets. In those cases, it is better to introduce a new Observer/Store pair that projects the relevant state for that subtree, so that only widgets that need to update are rebuilt, without needing to pass the state through more than one layer down the tree. (if you not componentize the widgets inside the `AppObserver` builder, that will not be an issue, as the everything inside the builder that uses the observable state will be rebuilt, like in MobX - But is strongly recommended to componentize).

### Alternatives Considered (not for the engine but for the overall presentation architecture)

#### A) MVVM with MobX

Pros:

- Familiar in the Flutter ecosystem.
- Good ergonomics for reactive UI.
- Fine-grained observables can be efficient and very useful for specific scenarios.

Reasons not adopted as the official architecture:

- Common MVVM usage mixes persistent state and ephemeral events.
- Typically leans on code generation and MobX concepts being part of the public architecture.
- Encourages fine-grained observables that can make screen-level reasoning harder when not bounded by a sealed state machine.
- In this project's adopted architecture, fine-grained observables can still exist as an implementation of a custom Store Template for specific cases if needed.

#### B) BLoC / Cubit

Pros:

- Strong unidirectional model.
- Clear separation of intent and state.
- Well-known patterns and libraries in the Flutter ecosystem.
- Highly testable with explicit events and states.

Reasons not adopted:

- Constrains the architecture to a specific pattern that may not fit all screen needs (e.g., complex screens with multiple state sources that require fine-grained control due to performance considerations), whereas the chosen Store-driven approach allows for more flexibility while still enforcing core principles.
- Boilerplate overhead (events, reducers/handlers) for many screens.

#### C) Provider-based reactive ViewModels / ChangeNotifier-style patterns

Pros:

- Simple to wire in Flutter.
- Low barrier to entry.

Reasons not adopted:

- Almost same issues as MVVM with MobX.
- As state complexity grows, manual dependency management becomes error-prone.

#### D) MVVM with Signals

Pros:

- Automatic dependency tracking and efficient updates.
- Very low boilerplate for reactive state management.
- No need for code generation or manual notification orchestration.

Reasons not adopted:
- Almost same issues as MVVM with MobX.
- In this project's adopted architecture, Store templates deals with the boilerplate and code generation issue, while providing clear contracts for screens.
- Signals ecosystem is currently less mature in Flutter, with fewer community resources, than other options.

#### E) Others
Reasons not adopted:
- Lead to similar issues as above. 

### Conclusion
The adopted custom Store-driven architecture does not depend on any specific reactive framework and allows for specialized observer/store pairs to handle complex UI patterns in a performant way without breaking the core unidirectional flow and separation of state/effects.
